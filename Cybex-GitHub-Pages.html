Welcome to Cybex — a cyber space for learners and curious people.

Cybex is built to make cybersecurity easier to explore without assuming you already know where to start. Follow the roadmap, practice in legal environments, build projects, and learn at your own pace.

Learn
Build computer, networking, Linux, Windows and security foundations.
Practice
Use CTFs, training platforms, local labs and systems you are authorized to test.
Build
Turn what you learn into projects, reports and useful tools.
Explore
Try Red Team and Blue Team paths when you are ready to specialize.
How Cybex works: Start with the Standard Roadmap. Click a phase to open its detailed checklist. Your local progress is saved automatically in this browser. If a Cybex backend is configured, you can also use accounts, cross-device progress, profile search and private messaging.

PHASE 0 — Computer Fundamentals

~2–4 weeks

Goal: understand what a computer actually does.

Hardware: CPU, RAM, storage, motherboard, GPU, peripherals
Binary, hexadecimal, bits/bytes, files and processes
Operating systems, kernels, applications, drivers
Filesystems, permissions, users and processes
Virtualization and virtual machines

Checkpoint: explain what happens from pressing a power button to opening a web page.

PHASE 1 — Networking

~3–6 weeks

Goal: understand how machines communicate.

OSI and TCP/IP models
Ethernet, MAC addresses, ARP
IPv4/IPv6, subnetting, CIDR
TCP vs UDP, ports and sockets
DNS, DHCP, HTTP/HTTPS, TLS
NAT, routing, firewalls, VPN concepts
Read packet captures in Wireshark

Checkpoint: capture a DNS + HTTP/HTTPS conversation in your own lab and explain each major packet.

PHASE 2 — Linux

~3–5 weeks

Goal: become comfortable living in a terminal.

Navigation, files, pipes, redirects and text processing
Users, groups, permissions and sudo
Processes, services, logs and package management
SSH and basic networking commands
Bash scripting fundamentals
Complete OverTheWire Bandit

Checkpoint: set up a Linux VM and administer it from the command line without relying on a GUI.

PHASE 3 — Windows + Active Directory

~3–6 weeks

Goal: understand the dominant enterprise endpoint environment.

Windows architecture, users, groups and permissions
PowerShell basics
Event Viewer, Windows logs and Defender concepts
Services, scheduled tasks and registry basics
Active Directory: domain, DC, OU, GPO, Kerberos, LDAP

Checkpoint: explain how a domain login works and where an administrator would investigate suspicious activity.

PHASE 4 — Programming + Automation

~4–8 weeks

Goal: write small programs instead of depending on someone else's tool.

Python syntax, variables, functions, loops and data structures
Files, JSON, exceptions and modules
HTTP requests and APIs
Regular expressions and parsing
Git: clone, branch, commit, diff, merge and push
Build 3 small security-related utilities for your own lab

Checkpoint: read unfamiliar Python and modify it safely.

PHASE 5 — Security Fundamentals

~3–5 weeks

Goal: learn the language and models used across security.

CIA triad, assets, threats, vulnerabilities and risk
Authentication vs authorization
Least privilege, defense in depth, zero trust
Hashing, encryption, digital signatures and PKI
Vulnerability management and patching
Logging, monitoring, detection and incident response
Read NIST CSF 2.0 at a high level

PHASE 6 — Hands-on Cybersecurity

~6–10 weeks

Goal: connect theory to controlled practice.

Complete TryHackMe Pre Security
Complete TryHackMe Cyber Security 101
Learn Nmap concepts in authorized labs
Learn Wireshark packet analysis
Learn basic vulnerability assessment
Learn web security fundamentals with PortSwigger labs
Write a report for every substantial lab

Cybersecurity Rules & Safety Standards

These rules define how this roadmap should be used. Cybersecurity skills are powerful; the goal is to build them responsibly, documentably, and inside environments where you have permission.

1. Authorization comes first.
Only test a computer, account, application, website, API, network, cloud resource, or device when you own it or have explicit permission to test it. “It is publicly accessible” is not the same as “I am authorized to test it.”
  • Use dedicated practice environments. Prefer CTFs, training platforms, local virtual machines, intentionally vulnerable applications, and systems specifically provided for security testing.
  • Never use another person's credentials. Do not attempt to access, guess, bypass, steal, reset, or reuse credentials that are not yours or that you were not explicitly authorized to handle.
  • Do not experiment on real-world targets. Avoid scanning, exploiting, brute-forcing, vulnerability testing, or automated probing against random websites, public IPs, school systems, company systems, game servers, or other networks without written authorization.
  • Protect data. Do not collect, copy, expose, publish, or retain private information that you encounter during testing. If sensitive data appears in an authorized lab, treat it as sensitive and follow the lab's rules.
  • Minimize impact. In an authorized environment, use the least disruptive technique necessary. Avoid actions that could delete data, interrupt services, change accounts, damage systems, or create unnecessary traffic.
  • Keep proof and scope. Before a lab or assessment, record what is in scope, what is out of scope, the allowed time window, and what actions are permitted. Keep notes of commands, observations, and results.
  • Learn the defensive side. For every offensive technique you study, understand what it does, what evidence it leaves, how defenders can detect it, and how the underlying weakness can be fixed.
  • Do not bypass safety controls just to “see if it works.” Security training should increase understanding without turning a learning exercise into unauthorized access or real-world harm.
  • Respect platform rules. Follow the terms, rules, and scope of the lab, CTF, bug-bounty program, school environment, or other service you are using. If a rule is unclear, stop and get clarification before testing.
  • Report responsibly. If you discover a vulnerability in an authorized environment, document the issue clearly, include reproducible evidence that is safe to share, explain the impact without exaggeration, and use the organization's stated reporting process.
Simple decision check: Before running a security action, ask: “Do I own this system, or do I have explicit authorization? Is this action inside the allowed scope? Could it expose data or disrupt service?” If any answer is unclear, do not run the action until the scope is confirmed.
